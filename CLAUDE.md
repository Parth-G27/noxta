# Noxta — Project Instructions

Email-based reminder/ping app. React SPA (`client/`) + Express API (`server/`) +
hosted Postgres, all TypeScript. See `/Users/bidarip/.claude/plans/lets-being-in-plan-effervescent-gizmo.md`
for the full end-to-end plan; this file holds only the durable, always-needed rules.

## THE RULE: this project is spec-driven

Before writing or editing any application code in `client/`, `server/`, or `shared/`,
there MUST be an approved spec in `specs/` with a task covering the change.

At the start of any request that would change application behavior:
1. Determine the active spec — check the current git branch (`spec/NNN-slug`).
2. If there is no active spec, do NOT start coding. Use the **sdd-spec** skill.
3. If a spec exists but has no `plan.md`, use **sdd-plan**.
4. If `tasks.md` has unchecked tasks, use **sdd-implement**.
5. If all tasks are checked, use **sdd-verify**.
If unsure where things stand, use **sdd-status** first.

### Exempt from the spec requirement
Cosmetic or non-behavioral work: formatting, comments, typo fixes in copy,
dependency bumps, pure refactors with zero behavior change, and genuine hotfixes
for a broken build. Use a `chore/` or `fix/` branch. If it changes observable
behavior, the API surface, or the database schema, it needs a spec — no exceptions.

### Scope discipline
Never implement something that is not in the active spec's `tasks.md`. If asked
mid-flight, stop and say so: either add a task (if it is already covered by an
acceptance criterion) or propose amending the spec / opening a new one.

## Stack
- Client: Vite 8, React 19, Tailwind v4, **TypeScript**, ESLint flat config, Vitest + React Testing Library + MSW
- Server: Node 24 LTS, Express 5, **TypeScript**, Drizzle ORM + drizzle-kit, Zod, Vitest + Supertest + Testcontainers-Postgres
- Shared: `shared/` workspace — Zod schemas + inferred types consumed by both client and server (one schema, two consumers)
- DB: hosted Postgres (Neon). Forward-only SQL migrations generated by drizzle-kit, committed under `server/drizzle/`.
- Monorepo via npm workspaces (`client/`, `server/`, `shared/`). Run `npm run verify` from the root (lint + test + build, all workspaces).

## Backend architecture — layer rules (non-negotiable)

```
server/src/
  index.ts          process entry: PROCESS_ROLE=web|worker|all, graceful shutdown
  app.ts             express app assembly; NO listen()
  container.ts       composition root — manual DI wiring, no container library
  config/            env.ts (the ONLY place process.env is read; Zod-validated), constants.ts
  db/                pool.ts, client.ts (drizzle), migrate.ts, transaction.ts
  models/            Drizzle table definitions
  repositories/       ALL SQL lives here. Returns plain objects. No business rules.
  services/           Business logic. Throws typed errors from utils/errors.ts.
                      schedule.service.ts is PURE — takes `now` as a parameter, never calls `new Date()`.
    email/            email.service.ts, providers/ (EmailProvider interface + resend/smtp/memory), templates/ (React Email)
  controllers/        HTTP <-> domain. Validate input, call service, shape response. No SQL, no req/res leaking into services.
  routes/v1/          Routers only: path -> middleware -> controller. Zero logic.
  middlewares/        requestContext, authenticate, validate, rateLimit, errorHandler, notFound
  validators/         Zod schemas (import from shared/ where the shape is shared with the client)
  workers/            scheduler.worker.ts, dispatcher.worker.ts, retention.worker.ts, runLoop.ts
  observability/       metrics.ts (prom-client), sentry.ts
  utils/              errors.ts, logger.ts, crypto.ts, datetime.ts (Clock port), backoff.ts
```

- Dependency direction is strictly `routes -> controllers -> services -> repositories -> db`.
  Never call upward. Never skip a layer.
- `req` / `res` / `next` MUST NOT appear below `controllers/`.
- Raw SQL MUST NOT appear outside `repositories/` and `db/`.
- Controllers never map errors to status codes. Throw a typed error; the central
  error middleware maps it.
- All external input is parsed by a Zod schema from `validators/` at the controller
  boundary. Services trust their inputs.
- Every query touching user-owned data takes `userId` as a required repository
  argument (e.g. `findById(id, userId)`) — ownership is structural, not a
  post-hoc check.
- Multi-statement writes go through the transaction helper in `db/transaction.ts`.
- `console.*` is banned in `server/` — use `utils/logger.ts` (pino).
- Secrets come from `config/env.ts` only, which Zod-validates at boot and exits
  before the server listens if anything is missing or malformed.

## Naming
- Server files: `<resource>.<role>.ts` — `reminders.routes.ts`, `reminders.controller.ts`,
  `reminders.service.ts`, `reminders.repository.ts`, `reminders.validators.ts`. Resource is plural.
- Tests sit next to the code: `reminders.service.test.ts`.
- DB: snake_case, plural tables, `id uuid pk`, `created_at`/`updated_at timestamptz`.
- API: `/api/v1/<plural-kebab>`. JSON is camelCase in and out; snake_case <-> camelCase
  mapping happens in the repository layer and nowhere else.
- Client: feature folders `client/src/features/<feature>/{api,components,pages}`, each
  with an `index.ts` barrel as its only public surface — other features import the
  barrel, never a feature's internals. Components `PascalCase.tsx`, hooks `useThing.ts`,
  network calls only in `client/src/lib/api-client.ts` + `features/*/api/`.

## Testing
- Vitest everywhere. `npm run verify` = lint + test + build across all workspaces.
- Every service function has a unit test. Every route has a Supertest integration test.
- Repository tests run against a real test Postgres, migrated in globalSetup, run
  inside a rolled-back transaction per test. Never mock the database for repository tests.
- **Every acceptance criterion must have at least one test whose name begins with its
  AC id**, e.g. `it('AC-3: rejects a reminder scheduled in the past', ...)`.
  This is how `sdd-verify` proves a spec is satisfied. There is no coverage-% gate
  project-wide; `schedule.service.ts` and `delivery.service.ts` are the two files
  where a bug is silent and expensive, so hold those to a high bar specifically.
- No `.only`, no `.skip`, no committed `TODO`/`FIXME` in changed code.

## Git
- One branch per spec: `spec/NNN-slug`. Application code never lands directly on `main`.
  `chore/<slug>` / `fix/<slug>` for spec-exempt work.
- Conventional Commits, scope = spec number, plus trailers:

  ```
  feat(001): add reminders repository

  Spec: 001-create-reminder
  Tasks: T004
  ```

- One commit per task. Tests ship in the same commit as the code they cover.
- Never commit with failing lint or tests.
- One PR per spec, titled `[001] Create a one-off email reminder`. Merge with `--no-ff`
  (not squash) so per-task history and `Spec:`/`Tasks:` trailers survive on `main`.
